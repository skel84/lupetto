## Scoped bootstrap decisions

- The first standalone CLI used Go 1.27.1 (the locally exercised toolchain), the temporary local module path `lupetto`, and the standard library only. The later generic selector adds a pinned apko 1.4.5 Go dependency for APK-compatible version comparison; the apko executable remains separately pinned for image builds. A public module identity and older supported Go versions remain undecided.
- At CLI bootstrap, exact-request parsing required an APK revision (`-rN`) but did not perform catalog lookup or image builds. The PostgreSQL 17 first-image path below subsequently resolved major/minor selectors; generic signed-index package/provider selection now supersedes its package restriction. Neither stage establishes a catalog or validated SBOM evidence.
- apko was absent at CLI bootstrap and was subsequently installed locally through Homebrew as 1.4.5 on macOS/amd64. Installing a tool does not pin the version for Lupetto builds or settle repository/keyring, image configuration, and build-evidence decisions.
- The `doctor` command checks executable discovery on `PATH` for apko and Docker (needed by the planned default image-build/load path), with Cosign optional for signing. Missing required tools produce a nonzero status; missing optional Cosign is reported without blocking. Advice is OS-specific, but the command never installs tools or asserts version/daemon compatibility. The first-image decision below pins apko for this build path.

## Scoped first-image decisions: PostgreSQL 17 (historical, superseded where noted)

- Initially mapped only `postgresql` to the exact Wolfi APK name `postgresql-17`. This package-only restriction is **superseded** by generic signed-index selection below. A missing match remains an error, not a substitute or archival fetch.
- Use the official Wolfi repository at `https://packages.wolfi.dev/os` and its [documented signing key](https://github.com/wolfi-dev/os#readme) at `https://packages.wolfi.dev/os/wolfi-signing.rsa.pub`; the key's observed SHA-256 is `f0031424cf46f7db780ce63a45f0fd6aa6f85f601e6bb3b7a91fe3d4d5b7d2cc`. Verify the downloaded APKINDEX signature against that pinned key **before** major/minor selection or unavailable-version reporting, and retain the signed archive and its SHA-256. apko also uses the pinned key without signature bypass and locks the selected exact package/checksum before image creation; if the live repository changed in between, fail rather than substitute.
- Use native apko 1.4.5 with an `x86_64` target on the exercised darwin/amd64 host, emit a local OCI layout, and retain its input config, index, key, and apko dependency lock in a unique user-cache build workspace. No runnable PostgreSQL recipe, Docker load, publication, signing, or validated SBOM is implied. Other host/target pairs remain unverified.
- Probe evidence: `apko lock --arch x86_64 --output <lock> <config>` and `apko build --arch x86_64 --sbom=false --vcs=false --lockfile <lock> <config> <tag> <existing-output-directory>/` produced an OCI layout with `postgresql-17` version `17.10-r1` in `usr/lib/apk/db/installed`. At the observed amd64 index snapshot, `17.1`, `17.2`, and `17.3` were absent. These upstream apko probes preceded the separate Lupetto build recorded in [verification](verification.md#scoped-postgresql-17-image-evidence).

## Generic signed-index selection (implemented image-only slice)

- Resolve a requested name from signed APKINDEX records whose APK `P` name matches exactly **or** whose `p` provides field declares that name at the same exact APK version. Requested virtual providers may be namespaced (for example, `cmd:curl` resolves to the real `curl` APK); validate their segments but validate actual APK names separately. This avoids package-specific aliases: Wolfi advertises `postgresql` through versioned APKs, `nginx` through mainline/stable APKs, and `valkey` through both unversioned and versioned APKs. Do not guess from arbitrary name prefixes or silently choose between equally ranked providers.
- A dotted numeric selector (major, minor, or patch) matches the corresponding leading upstream numeric components; choose the highest matching APK version and packaging revision using apko's pinned APK-compatible version comparator, not lexical or generic SemVer sorting. `--apk-version` requires an exact revision. No match is an explicit unavailable-version error; equal-ranked distinct package/byte candidates are ambiguous errors. The signed index is retained and apko still locks the exact selected package and checksum before image composition.
- Keep the same image-only apko pipeline and user-cache workspace for every requested package. nginx and Valkey are real interoperability checks, not source-level package allowlists or product recipes. Numeric selector support does not imply full package-family mapping for every Wolfi naming convention, a generic catalog, or runnable images.

## Live signed-index discovery (scoped CLI command)

- `lupetto discover <package-or-provider>` reads the current Wolfi APKINDEX for the host architecture, verifies its signature using the same pinned key as `build`, and lists each complete record with exact APK `P` name and `V` version matching the requested name or its same-version `p` provider. Sort by APK-compatible version descending, then by actual package name for equal versions; show the signed archive SHA-256 and architecture. Reject missing/invalid names and report no matches explicitly. Do not invent package-family mappings, omit older matching entries, or silently resolve ambiguity between equal-version providers.
- Discovery reads metadata only: it does not invoke apko, create a build workspace, check downloadable APK bytes or dependencies, or claim every listed version is buildable. This is **not** snapshot ingestion, historical archive support, machine-readable Explorer output, or a second build pipeline. Exact builds still resolve and validate their own index, lock, and image independently.

## Exact-build SPDX evidence decisions (current milestone)

- Keep the existing minimal apko configuration, verified Wolfi index/key, exact selection, and single-architecture lock/build path. Use native apko 1.4.5 `build --sbom-path <workspace>/sbom --sbom-formats spdx` with the resolved lock; an explicit output path keeps apko 1.4.5's SPDX files in the private workspace rather than the invocation directory when writing an OCI layout. Retain `sbom-x86_64.spdx.json` as the validated architecture document and `sbom-index.spdx.json` as supplemental, **not independently lock-validated**, index evidence.
- Compare the lock's complete `contents.packages` set of `(name, version, architecture)` identities (reject missing fields/duplicates) with apko's SPDX 2.3 architecture document. apko 1.4.5 emits a `distro=wolfi` APK purl for every locked package and may also emit a separate `origin=...` APK purl derived from the installed APK database for each package. Require the `distro` set to equal the lock; if any `origin` entries are present, require that set to equal the lock too. Allow one entry per identity in each set, never treat the two kinds as duplicate packages. Require the matching `arch`, Wolfi namespace, and package name/version; reject missing/extra/changed identities and malformed or ambiguous APK references. Container image/layer, OS, and build-recipe entries are legitimate non-APK entries and are excluded from this comparison; they are not certified by it. This is lock consistency, not an independent audit of every installed dependency or proof that a discovered version is buildable.
- Continue using a unique mode-0700 user-cache workspace with mode-0600 inputs and retained image, lock, generated SPDX, and checksum. On success, write `result.json` with a versioned local evidence record (snapshot SHA-256, selected APK name/version, target architecture, apko version, artifact paths, validated SPDX SHA-256). Failures retain partial files and print the workspace but write no success result or claim validated evidence. This local record is not an Explorer compatibility protocol; that contract remains open.
- `lupetto sbom <package-or-provider> --apk-version <exact-revision>` uses the **same** signed-index resolution, lock, image composition, and validation as `build`, then reports the validated SPDX file. apko 1.4.5 generates the architecture document during composition, so no alternative metadata-only SBOM is claimed. Numeric selectors for `sbom`, Docker loading, and publication remain outside this slice.

## Local Docker loading decisions (resolved before implementation)

- `build` loads into the configured local Docker daemon by default; `--no-load` is a valueless, single-use build flag that skips Docker entirely. Keep `sbom` image-only through the same exact-build function; reject `sbom --no-load` rather than silently broadening that command's flags. No daemon start, Docker context changes, registry access, credentials, publication, or signing are part of this milestone.
- Initially exposed only `lupetto/local:build-<workspace-suffix>`, using the unique `image-<suffix>` workspace identifier. The user-approved readable-reference decision below supersedes that as the main displayed name, while retaining it for composition/import and per-build traceability. Registry naming remains a separate decision.
- After the existing OCI package check and lock/SPDX validation, export the already-built single image as a Docker-compatible archive with `go-containerregistry v0.22.1` (the version pinned by apko 1.4.5), then run `docker image load --input <workspace>/docker-image.tar`. This is format conversion, not another apko invocation or build path. Retain the archive for diagnostics. Inspect the exact reference after loading and require a valid local image ID and matching OS/architecture; do not parse human-readable load output as identity proof. If the inspected ID equals the source OCI config digest, identity is directly established. Otherwise save that exact imported reference with `docker image save --output <workspace>/docker-loaded.tar <reference>` and require the saved image's config digest to equal the source OCI config digest using the upstream archive reader. Retain the saved archive privately. Never accept an unrelated ID solely because loading returned zero.
- The initial assumption that Docker's inspected `.Id` always equals its config digest was **replaced after a real failed smoke**: Docker 27.4.0 with its containerd image store returned the imported Docker-schema-2 manifest digest as `.Id`, while `docker save` preserved exactly the source config and layer bytes. The fallback verifies content rather than guessing a backend-specific ID transformation. The result's local image ID is Docker's inspected identifier, not necessarily a config digest and never a registry publication identity.
- The first local-loading result used version 2 with one local image reference, separate Docker-load status (`loaded` or `skipped`), and the verified local image ID when loaded; readable naming below extends this to version 3 with both references. This ID is **not** a pushed registry digest. Write `result.json` and print successful image/SPDX/load outcomes only after every requested stage succeeds; no-load and SBOM success explicitly say loading was skipped. This is not an Explorer compatibility contract.
- Load/archive/inspect/saved-identity failures return nonzero, identify the failed stage, local reference, and retained workspace, and write no success record or validated-evidence success output. State that composition completed but loading was not confirmed. Cancellation propagates through external commands and archive writes; check cancellation before final success recording. Once a load has begun, failure/cancellation may leave an imported image/tag; do not claim rollback or automatically delete images. If loading was confirmed but result recording fails, report that partial local success explicitly.
- Preserve non-secret diagnostics; do not persist Docker configuration, environment values, or credentials. External command cancellation is best-effort: stopping the client cannot undo daemon work. Verification evidence and unexercised cases belong in [verification](verification.md#local-docker-loading-evidence) and the single checklist.

## Readable local image references (user-approved)

- Make `lupetto/<resolved-actual-apk-name>:<exact-apk-version>-<oci-architecture>` the primary operator-facing reference, for example `lupetto/busybox-static:1.38.0-r2-amd64`, `lupetto/postgresql-17:17.10-r1-amd64`, or `lupetto/nginx-stable:1.30.2-r0-amd64`. Derive it only after signed-index selection, from the actual APK identity rather than a requested provider/selector. Map `x86_64` to `amd64` and `aarch64` to `arm64` using the existing architecture mapping. Validate with the pinned upstream Docker reference parser.
- Preserve generic APK selection when an exact name/version cannot be represented directly in Docker syntax. Use deterministic, collision-resistant SHA-256 component fallbacks instead of lowercasing, replacing characters lossily, truncating, substituting an APK, or failing an otherwise supported selection. Reserve `apk-sha256-` for fallback repository components (names starting with that prefix also use the fallback); tag fallbacks start `_apk-sha256-`, which cannot be confused with ordinary APK versions beginning with an alphanumeric character. Retain/display the unchanged exact APK name/version in evidence. Ordinary Docker-compatible identities retain the literal requested format.
- Keep `lupetto/local:build-<workspace-suffix>` as the unique additional reference. Compose/export/load and verify through this reference first, reusing the existing pipeline and saved-config identity fallback. After confirmed import, use `docker image tag <verified-local-image-ID> <readable-reference>`, then inspect the readable reference and require that same local ID/platform. Tag from the verified ID, not from a mutable reference. Do not add another build, registry operation, image cleanup, or automatic migration/retagging of older images.
- The readable version tag is intentionally mutable: a later successful build can replace it because dependencies, snapshot, or inputs may differ at the same top-level APK revision. The unique build tag and retained workspace preserve the earlier build reference; neither tag is a registry publication digest. Concurrency does not create an atomic multi-tag transaction: identity verification can fail if another build replaces the readable tag during finalization, and a previously successful readable tag can move later.
- Add both references to a version-3 private local result: `imageReference` is the readable primary name and `buildReference` is the unique name; preserve selected APK, snapshot, artifacts, validation, and loaded/skipped fields. Print both in the final successful CLI summary and selection progress. No-load and `sbom` record/display the intended names but do not invoke Docker or claim either is loaded. This remains a private record, not an Explorer compatibility contract.
- A readable tag/inspect failure or cancellation returns nonzero, writes no success record, and reports that the unique image was imported/verified while readable tagging was not confirmed and may already have changed local tags. Preserve stage/reference/workspace diagnostics and do not attempt rollback. Final result-record failures after both tags are confirmed report partial local success as before. No schema migration or change to `sbom` loading semantics is part of this request.
- Verification belongs in [verification](verification.md#readable-local-image-reference-evidence) and the single checklist: test ordinary/provider/architecture derivation, safe fallback identities, tagging from verified ID, dual-reference outcomes, no-load/SBOM, and tag/inspect/cancellation failure reporting; exercise a real local build with both references.

## Live build feedback decisions

- `build` and `sbom` report human-oriented stage progress on stderr by default, alongside live apko lock/build and Docker load output. Keep stdout's final artifact/evidence/load summary success-only; feedback itself does not change the evidence schema (the later readable-naming request introduces version 3). Discovery/doctor are unchanged. No new verbosity flags or persistent log artifact are needed for this request.
- In an interactive stderr terminal, show an ASCII spinner with the active stage and elapsed time while work is underway; clear/redraw it around live log output and stop/clear it before final success or failure reporting. Redirected stderr and `TERM=dumb` receive plain logs with no animation or terminal control sequences. Do not invent percentage completion.
- Keep each animated frame within the terminal width, leaving the last column unused to avoid autowrap; re-read the width for resized terminals. Use a conservative 80-column fallback when dimensions cannot be obtained, and suppress frame content if the terminal is too narrow. Full static stage/tool logs may wrap normally, but animation must not create scrolling.
- Stages cover tool check, workspace, index/key fetch and verification, exact selection, apko lock/composition, installed-package/SPDX validation, Docker archive/load/identity verification (including the saved-config fallback), and final result recording. Report exact selection and local references before composition, but do not claim validated SPDX or successful loading before those requested stages finish. Keep no-load/SBOM semantics; local names and any readable-tag stages follow the user-approved naming decision above.
- Stream only the actual lock/build/load tool diagnostics. Tool-version output and Docker inspect identity JSON remain internal parsing inputs. Never print process environment, full command arguments, Docker configuration, or credentials; do not add credential-bearing operations. Keep captured tool failures available and preserve cancellation/partial-success semantics.
- Progress rendering is CLI-owned presentation, not another execution engine. Serialize log/spinner writes, stop and join renderer work on success/failure/cancellation, and ensure a rendering failure does not turn a successful build into a false tool failure. Verification must cover live delivery before tool completion, plain-output behavior, terminal animation/cleanup, and failure/cancellation; record observed results in [verification](verification.md#live-build-feedback-evidence).

## Publication-first roadmap (user-approved)

- Prioritize generic registry publication, then Cosign image signing and a signed `spdxjson` attestation of the already-validated architecture SPDX, both bound to the same pushed immutable registry digest.
- Use the existing live signed-index discovery/selection and single exact-build pipeline. Preserve signed-index/key, exact APK revision, dependency lock, validated SPDX, and per-build provenance; no persistent database is required for correctness of this workflow.
- Defer persistent snapshot ingestion, SQLite catalog queries, and historical selection until there is a concrete catalog/history or Explorer need. This changes implementation priority and the standalone CLI release gate, not the full compatibility scope: catalog and Explorer targets remain pending rather than being deleted or marked complete.
- Historical metadata can support comparisons, pinned snapshot selection, and browsing, but does not preserve APK bytes or guarantee historical rebuildability. Existing per-build evidence retention remains required.
- The immediate prerequisite decisions are registry naming/prefix validation, configuration precedence and incomplete-input errors, pushed-digest capture, separate stage/partial-success reporting, and supported Cosign signing/attestation/verification behavior. Local readable tags do not settle registry naming or establish immutable publication identity.
- Implement and verify coherent checkpoints: registry publication first, then signing/attestation and their verification. Preserve Docker credential-store authentication, process-environment `COSIGN_PASSWORD`, and clearly separated production HTTPS/transparency-log requirements versus local-development exceptions. (Publication's original rejection of `--no-load` is superseded by [direct OCI publication](#direct-oci-publication-unified-result-record-and-package-layout-user-approved-2026-10-01).)
- This priority approval does not authorize publication/signing against a live registry, use of existing credentials/keys, or remote infrastructure changes. Obtain authorization for the exact verification target/scope; prefer isolated local checks. The [implementation checklist](implementation-plan.md) remains the single progress record.

## Registry publication contract (resolved before implementation)

These are the contract for the first publication checkpoint. **Superseded in part:** the Docker tag/inspect/push/pull/save, push-summary parsing, and `--no-load` rejection bullets below are replaced by [direct OCI publication](#direct-oci-publication-unified-result-record-and-package-layout-user-approved-2026-10-01); naming, validation, precedence, and partial-outcome rules still apply.

- Only `build` accepts `--registry` / `LUPETTO_REGISTRY` and `--repository` / `LUPETTO_REPOSITORY`. Resolve each setting independently: an explicitly supplied flag overrides its environment input, including an explicitly empty value; reject that empty flag rather than reviving its environment input or silently disabling publication. Empty/unset environment inputs mean absent. Both effective settings absent means publication is skipped; exactly one nonempty setting is an incomplete-configuration error. Reject duplicate flags, invalid values, and publication with `--no-load` before tool checks, workspace creation, network activity, or other build/publication side effects. `sbom` rejects all explicit publication/signing flags and ignores their environment inputs, preserving its image-only contract.
- Registry input is an authority, not a URL: no scheme, user information, path, query, or fragment. Accept validated DNS names, IPv4, and bracketed IPv6, with an optional decimal port in the range 1–65535. Require an unambiguous registry spelling: a DNS name containing a dot, `localhost`, an IP address, or a single-label DNS name with an explicit port. Do not silently interpret an ambiguous bare name as a repository on Docker Hub or accept an upstream normalization that changes the intended authority.
- Repository input is a nested lower-case OCI prefix, such as `team/lupetto/images`, not a complete tagged image reference. Reject empty, leading/trailing/repeated-slash, `.`/`..`, uppercase, tag, and digest components. Validate the entire eventual reference with a deliberately pinned `github.com/distribution/reference` dependency, not only individual components; reject normalization that changes the requested registry/repository. Fail if the full repository name exceeds the upstream parser's bound; do not truncate or hash an operator-supplied registry/prefix to evade it.
- Derive the remote repository as `HOST/PREFIX/<APK-component>`, using exactly the same resolved actual-APK component as the local readable repository (including its deterministic SHA-256 fallback when needed). Reuse the **same** local literal-or-fallback exact-version/OCI-architecture tag, then append `-build-<workspace-suffix>` for the unique remote tag. If that combined tag exceeds upstream syntax/length limits, use a deterministic SHA-256 fallback for the entire combined tag; never truncate, resolve another APK, or use a mutable remote readable alias as publication identity. Retain/display the unchanged exact APK name/version regardless of either fallback.
- Run `docker image tag <verified-local-image-ID> <unique-remote-reference>` from the already verified ID, never from the mutable local readable alias. Inspect the unique remote tag and require that verified ID and expected OS/architecture before `docker image push <unique-remote-reference>`. Use Docker's existing credential-store authentication only: no `login`, credential arguments, credential/config collection, or custom registry authentication path.
- Parse exactly one supported Docker 27.4 push digest summary for the expected unique tag, containing a valid `sha256` digest. Reject absent, conflicting, multiple (even repeated), wrong-tag, or malformed summaries rather than choosing the last apparent digest. A successful push command alone is not identity proof. Construct the pushed immutable reference as `REPO@sha256:<digest>`, not a local Docker ID.
- Use a separate secret-safe publication subprocess adapter for auth-bearing Docker commands, not the capturing/live local executor. Discard tool diagnostics rather than capturing, streaming, attaching them to errors, or retaining command transcripts. For push only, feed stdout to a bounded streaming parser for the expected unique-tag summary; retain only the validated digest, never the full stdout or unmatched lines. Parser errors and process failures expose only non-secret stage/status information. Do not persist environment, Docker configuration, or credential-helper output.
- Pull that immutable reference with Docker, then `docker image save` the immutable image into a retained mode-0600 archive. Require the saved config digest to equal the original OCI image config digest, and hash the **actual saved layer bytes**, uncompressed and in manifest order, requiring their ordered SHA-256 hashes to equal the source OCI config's `rootfs.diff_ids`. Comparing only the saved config's claimed diffID array is not proof of saved-layer content. Reject changed config/layers, ambiguous/malformed archives, or platform mismatches. Registry transport may change manifest serialization without changing this built-image identity; never require the pushed manifest digest to equal the local image ID.
- Keep publication outcomes separate from composition/loading: `skipped`, `published`, or `failed`, with the captured pushed digest/immutable reference separate from its identity-verification outcome. Report publication successful only after immutable pull/save/content verification. Preserve a successfully captured pushed digest if later verification fails, but mark identity unverified and never allow signing or attestation until verification succeeds. Failures/cancellation after tagging, pushing, or verification explicitly report confirmed local stages and possible remote/tag/pull side effects; a push can have happened even if digest capture or verification fails. Retain the workspace, print no complete-success result, and do not attempt rollback. A final record failure after confirmed publication reports that partial success.
- Return a typed `workflowFailure` carrying non-secret, separate composition/loading/publication/identity-verification/signing/attestation outcomes, retained workspace, and any captured pushed digest. The CLI must consume that type rather than parse an error string or discard partial outcomes; report confirmed and failed/unconfirmed stages separately. Write these sanitized partial outcomes to a separate mode-0600 `failure.json` when a workspace exists; `result.json` remains success-only after every requested stage succeeds. Failure-record writing must not hide the original stage failure or turn partial success into complete success.

## Cosign signing contract (chosen for the next checkpoint)

This records the contract chosen for the checkpoint after registry publication. Lupetto implements this signing/attestation path, with [observed installed-CLI local HTTP/offline proof and passing combined focused race-enabled/full Go test gates](verification.md#local-cosign-signing-and-spdx-attestation-evidence). The decision history below is retained; neither those prerequisites nor the scoped local completion imply keyless support, blanket registry/host/version compatibility, or production HTTPS/TUF/Rekor verification. The separate production-verification acceptance gate remains open and requires explicit target/credential authorization.

**Superseded in part:** signing no longer requires local loading; `--no-load` with signing is valid under [direct OCI publication](#direct-oci-publication-unified-result-record-and-package-layout-user-approved-2026-10-01). Version 5 records are replaced by version 6.

- Support exactly upstream Cosign **v3.1.3**, checked before requested signing work. Signing requires an explicit effective `--cosign-key` / `LUPETTO_COSIGN_KEY`; an optional `--cosign-signing-config` / `LUPETTO_COSIGN_SIGNING_CONFIG` selects an upstream signing-config file, and key/config are valid together. Independently applied explicit flags override environment values, including empty values; reject explicitly empty key/config flags rather than falling back to environment values or silently disabling signing. Empty/unset environment inputs mean absent. Reject duplicates and invalid settings before tools/workspaces/side effects. Do not introduce a Lupetto signing-config schema or key store, or require a config when a key is supplied.
- `--cosign-allow-http` / `LUPETTO_COSIGN_ALLOW_HTTP` is a strict boolean setting: accept only `true` or `false` in nonempty environment or explicit flag values (a valueless flag means `true`); explicit `false` overrides environment `true`, and an explicitly empty value is invalid. Signing is build-only and requires publication plus local loading. Signing-config or enabled HTTP mode without a key is an error; a key without complete publication settings or with `--no-load` is an error. `sbom` rejects explicit signing flags, including explicit false/empty forms, and ignores their environment inputs.
- Pass key/config paths using explicit argument arrays. Inherit `COSIGN_PASSWORD` from the process environment only: never supply a password argument, print its value, persist environment/config/key contents, or collect credentials. Use the separate secret-safe subprocess adapter, discarding **all** Cosign stdout/stderr without live delivery, captured diagnostics, error attachments, or retained transcripts, since upstream failures can contain secret-bearing inputs. Report only the sanitized stage, immutable image reference, exit/failure status, confirmed preceding stages, and retained workspace through the typed workflow outcome.
- Invoke `cosign sign --yes --key <key> [--signing-config <config>] [--allow-http-registry] <immutable-reference>`, then `cosign attest --yes --key <key> [--signing-config <config>] [--allow-http-registry] --type spdxjson --predicate <validated-architecture-SPDX> <same-immutable-reference>`. Recheck the already lock-validated architecture document's recorded SHA-256 immediately before attestation; do not regenerate SPDX or attest the supplemental index document. Distinguish published, signed, and attested outcomes and uncertain side effects if either Cosign stage fails; no rollback or complete-success claim after a partial outcome.
- Apply a conservative Lupetto preflight policy: signing against a literal-loopback registry requires explicit effective `cosign-allow-http=true`, even if that registry might support HTTPS, so the local HTTP exception is opted into and clearly labeled. Reject enabled HTTP allowance for every non-loopback registry. Recognize only `localhost` or an IP literal for which `net.ParseIP(...).IsLoopback()` is true, using the existing validated registry authority and its bracketed-IPv6 validation; DNS resolution to loopback is insufficient. This setting is not TLS-verification bypass or a generic production insecure mode.
- For production non-loopback registries with no explicit signing config, preserve upstream HTTPS, TUF-provided signing/service configuration, and transparency-log defaults. An operator-supplied signing config can change services and cannot be described as proof of production transparency-log behavior. Absence of upstream `--allow-http-registry` does **not** establish HTTPS on loopback: the upstream verification probe below succeeded against HTTP without it.
- Use upstream v3.1.3's default registry compatibility mode, including its modern bundle/referrer behavior; do not force deprecated legacy or experimental registry flags. The initial synthetic sign/verify against upstream `registry:3` exercised that default mode but was not Lupetto signing or SPDX attestation interoperability. The subsequent [installed-CLI local proof](verification.md#local-cosign-signing-and-spdx-attestation-evidence) exercised both signing and SPDX attestation in that same default mode; it does not establish compatibility with every OCI registry.
- For a clearly labeled local/offline exception, generate the config using upstream `cosign signing-config create --out <FILE>` without services or `--with-default-services`. Do not hand-author a custom schema or use deprecated `--tlog-upload=false` / timestamp-service flags. This removes configured signing services for the test and does not prove production HTTPS/TUF/Rekor operation or public inclusion/auditability.
- Upstream v3.1.3 encrypted throwaway-key generation and no-service config generation through the upstream CLI were exercised outside the repository with inherited `COSIGN_PASSWORD`; the config is Sigstore protobuf v0.2. Parent-observed synthetic-image signing with that config and verification with the trusted throwaway public key against the isolated authenticated `127.0.0.1` HTTP `registry:3` succeeded in default v3.1.3 registry mode. Verification also succeeded **without** `--allow-http-registry`, using the explicitly local `--insecure-ignore-tlog` exception. No production HTTPS or Rekor verification was exercised. ## Direct OCI publication, unified result record, and package layout (user-approved 2026-10-01)

The user approved replacing the Docker publication sequence, allowing `--no-load` with publication/signing, removing Docker push entirely, and introducing one versioned result record with `--json`. This supersedes the Docker tag/inspect/push/pull/save bullets of the [registry publication contract](#registry-publication-contract-resolved-before-implementation), the `--no-load` rejection in the [publication-first roadmap](#publication-first-roadmap-user-approved) and [signing contract](#cosign-signing-contract-chosen-for-the-next-checkpoint), and the private version 3/4/5 records. Registry/repository settings, naming, fallbacks, Cosign behavior, and HTTP consent rules are unchanged.

- **Push the validated layout directly.** Publication pushes the single validated image manifest from the apko OCI layout with the pinned `go-containerregistry` v0.22.1 to the unique `HOST/PREFIX/<APK-component>:<tag>-build-<suffix>` reference. The manifest bytes are pushed unchanged, so the pushed digest is the local OCI manifest digest; it is known before pushing rather than parsed from tool output. Docker is not involved in publication, and there is no Docker publication fallback.
- **Verify by readback before signing.** A successful upload is not verification: the client accepts a successful manifest PUT without checking a returned digest or reading content back. After pushing, fetch the manifest by digest and require its bytes to hash to the digest and equal the local manifest; require the unique tag to resolve to that digest; fetch the config by digest and require it to equal the source config; fetch every layer by digest, hashing the compressed bytes against the manifest digest and the uncompressed stream against the source `rootfs.diff_ids` in order. Only then is publication `published` and verified. A failed readback keeps the digest recorded as unverified and blocks signing.
- **Authentication** reads only Docker's client configuration (`DOCKER_CONFIG` or `~/.docker/config.json`, including `credsStore`/`credHelpers`) through a small Lupetto keychain using `github.com/docker/cli/cli/config`, with the same lookup as go-containerregistry's default keychain. Unlike `authn.DefaultKeychain`, it never falls back to Podman/containers auth files (`REGISTRY_AUTH_FILE`, `$XDG_*/containers/auth.json`). Lupetto still performs no login, accepts no credentials, and copies no configuration. Daemon-only settings (`insecure-registries`, daemon `certs.d`, daemon proxies) no longer apply; the host trust store and process proxy environment do, as they already did for Cosign. Reference parsing must agree between `distribution/reference` and go-containerregistry; the only accepted difference is `docker.io` ↔ `index.docker.io`. Loopback registries are parsed with go-containerregistry's insecure option so every loopback literal (not only `127.0.0.1`) can use the HTTP fallback.
- **HTTP is loopback-only.** The upstream client would fall back to HTTP for RFC 1918, `*.local`, and loopback registries. Lupetto's transport rejects every plain-HTTP request whose host is not `localhost` or a loopback IP literal, matching Docker's default `127.0.0.0/8` exception. Signing still requires explicit `--cosign-allow-http` on loopback.
- **Errors stay sanitized.** Publication errors report the stage plus, at most, a Lupetto-chosen classification and the HTTP status with registry error codes limited to the known OCI distribution constants (registry-supplied codes are attacker-controlled strings, so pattern matching is insufficient). Registry bodies, messages, URLs with tokens, and credential-helper output are never reported or retained. The fetched manifest is retained as mode-0600 `published-manifest.json`; `docker-published.tar` is no longer produced.
- **`--no-load` is allowed with publication and signing.** Loading (when requested) still happens before publication and remains a separate outcome; publication no longer requires or uses a Docker image ID.
- **One record schema, version 6.** `result.json` (success) and `failure.json` (failure) share one schema with `version: 6`, `command`, `outcome` (`succeeded`/`failed`), optional `failure` (stage, sanitized error, side-effects-possible), workspace, request, selection, evidence, and per-stage outcomes for build, load, publication, signing, and attestation. Requested-but-unreached stages are `not-attempted`; unrequested stages are `skipped`. Every workflow, not only publication, now writes `failure.json` when a workspace exists. Version 3–5 records are not migrated.
- **`--json`** on `build` and `sbom` prints exactly that version-6 document to stdout on success and on post-validation failure, instead of the human summary; stderr progress is unchanged. Invocation errors (exit 2) print nothing to stdout. Changing the document's meaning requires a new version. This is the CLI's machine-readable result; Explorer compatibility rules (supported versions, cancellation, concurrency) remain an [open Explorer decision](#before-explorer).
- **Package layout.** Move signed-index access and selection to `internal/wolfi`, and the exact-build pipeline (composition, validation, loading, publication, signing, records) to `internal/build`; `cmd/lupetto` keeps argument parsing, terminal progress, and output. Both are module-internal; this does not settle Explorer packaging or create a public Go API.

## Registry-comparison dashboard (user-approved 2026-10-01)

The user approved a dashboard that compares the images Lupetto has published to a registry with the latest versions in the signed Wolfi index, shows known security fixes those images are missing, and builds new images from the UI. It must run as one container with no database; Kubernetes and Tekton/Konflux compatibility is the long-term direction. This supersedes the scope non-goals "registry-discovery UI" and "vulnerability scanning" (replaced by the bounded security-fix comparison below) and the rule that the UI must not display registry contents. It resolves several [Explorer open decisions](#before-explorer).

**Boundary.** The dashboard is a separate program, `lupetto-explorer` (`cmd/lupetto-explorer`), in this repository and Go module, shipped in one container image with the CLI. It imports no `internal/build` or `internal/wolfi` code: it obtains every index, registry, and security fact through `lupetto … --json` and builds through `lupetto build`. The comparison logic lives in the CLI so it also works from scripts and future Tekton tasks.

**Image identity annotations.** Every image Lupetto builds carries manifest annotations recording what it contains, so the registry can be read back without parsing tags (tags may use SHA-256 fallbacks):

| Annotation | Value |
| --- | --- |
| `org.opencontainers.image.version` | exact APK version, e.g. `17.10-r1` |
| `org.opencontainers.image.created` | build time, RFC 3339 UTC |
| `lupetto.apk.name` | actual resolved APK name, e.g. `postgresql-17` |
| `lupetto.apk.version` | exact APK version |
| `lupetto.apk.architecture` | APK architecture, e.g. `x86_64` |
| `lupetto.index.sha256` | SHA-256 of the signed APKINDEX archive used |

The `lupetto.` prefix is provisional until a public module/domain identity is chosen; changing it requires a status-output version bump. Images without these annotations (built before this change) are reported as unidentified, not guessed from tags.

**Products file.** A YAML file (`version: 1`) lists the tracked products, each a package name or provider plus one or more dotted numeric selectors; each pair is one *track*:

```yaml
version: 1
products:
  - package: postgresql
    selectors: ["16", "17"]
  - package: nginx
    selectors: ["1.30"]
```

Unknown fields are rejected. Registry and repository settings are not in this file; they keep the existing `--registry`/`--repository` flags and `LUPETTO_*` environment precedence. Products here are grouping/tracking only, not runtime recipes.

**`lupetto discover --json`.** `discover --json <name>` prints the existing discovery result as a versioned JSON document. `discover --json` without a name lists every package name in the verified index with its latest version and description, for browsing. Human output is unchanged.

**`lupetto status`.** `lupetto status --products <file> [--registry … --repository …] [--json]` reads the verified signed index, the registry, and the Wolfi security feed, and reports per track:

- the newest index APK for the selector (or an unavailable/ambiguous error for that track only; other tracks still report);
- the images in `HOST/PREFIX/<component>` for that APK name whose annotations match the selector: digest, tags, version, created time; non-image artifacts and unidentified images are counted, not parsed further;
- the newest built image (highest APK version, then newest created time) and its full installed package set, read from the image's `usr/lib/apk/db/installed` through digest-addressed registry reads and cached by digest (images are immutable);
- packages in that image with newer versions in the index, and **missing security fixes**: for each installed package, CVE/GHSA/Go vulnerability IDs listed in the security feed under a fixed version that is newer than the installed version and available in the index;
- a state: `not-built`, `update-available` (newer top-level version), `fixes-available` (same top-level version, but a rebuild would pick up security fixes), `current`, or `error`.

Registry reads reuse the publication keychain, loopback-only HTTP guard, and sanitized errors. `status` is read-only: no build, push, or signing. The JSON document is versioned (`version: 1`) and is the dashboard's contract.

Status exit semantics (implemented for this CLI checkpoint): exit 0 means the global comparison completed, including when individual tracks have `error` states or require updates/fixes. Consumers must inspect every track's `state` and `error`; exit 0 does not mean every image is current. Invalid invocation, registry configuration, or products YAML exits 2 with no JSON. Global failures (including index verification or security-feed fetch/parse failure) exit 1 with no partial status document.

Selector-reachability clarification (user-approved during implementation): retain all missing-fix facts whose fixed version is available anywhere in the current same-name/same-architecture index, even when a top-level fix is outside this track's numeric selector. Every fix carries `reachableByTrack`: top-level fixes are reachable only through the track's selected APK version; dependency fixes retain the index-availability rule. `fixes-available` is derived only from reachable fixes when the top-level version is unchanged. A `current` track may therefore still list unreachable top-level fixes, which the dashboard must show as warnings rather than presenting a clean security result. This is an index-based rebuild comparison, not an independently solved future dependency lock.

If the newest annotated image's top-level version is newer than the current track's index selection, report a track-level `error` with the image/comparison facts retained rather than implying a rebuild would preserve an unavailable top-level version.

Malformed secdb-version handling (user-approved after the live feed exposed `opa-envoy` fixed key `1.1.0-r1-r0`): never invent APK ordering for an unparseable fixed-version key. Skip it from evaluated missing-fix/state comparisons, but include `security.unevaluatedFixCount` and `security.unevaluatedFixes` with package name, original fixed-version key, and advisory IDs. If that exact package is installed in a track, also include its `unevaluatedFixes` with installed version/architecture. Human output warns explicitly. These warnings are not clean/security-current evidence; malformed YAML/JSON, invalid package identities, duplicate feed packages, exceeded bounds, and fetch/verification failures remain failures.

Advisory-ID handling (review correction): evaluate `CVE-YYYY-NNNN`, `GHSA-xxxx-xxxx-xxxx`, and `GO-YYYY-NNNN` IDs. A nonzero fixed-version entry with no recognised IDs is retained in the same global/affected-track unevaluated path, including its original unsupported IDs, rather than silently omitted. Mixed entries retain recognised IDs for evaluated comparisons. Empty or unsupported-only ID lists are not clean-security evidence, even if the APK version itself parses and the track state is `current`.

**Security data source.** Wolfi's `https://packages.wolfi.dev/os/security.json` (secdb format), fetched over HTTPS and identified by its SHA-256 in the status output. It is APK-version-aware, unlike NVD, whose product matching is unreliable for distribution packages. Limitations, shown in the UI and docs: the feed is not signed; it lists **fixed** vulnerabilities only, so an empty result does not mean an image has no vulnerabilities; it covers Wolfi packages only. This is not a vulnerability scan.

**Dashboard behavior.** Pages are rendered by the Go server (`html/template`, embedded assets, minimal JavaScript). Pages: overview of tracks and states, track detail (images, outdated packages, missing fixes), package browser (from `discover --json`), and build jobs (live log, result record). Status is computed in the background and cached with a manual refresh; the page shows when it was computed.

- Flags: `--listen` (default `127.0.0.1:8080`), repeatable `--allowed-host` (HTTP host or host:port allowlist), `--products`, `--lupetto-binary` (default `lupetto` on `PATH`), `--enable-builds` (default off). Registry, repository, and Cosign settings reach the CLI through the inherited `LUPETTO_*` and `COSIGN_PASSWORD` environment, never arguments.
- Builds run `lupetto build <package> <selector-or---apk-version> --no-load --json` with publication (and signing when a key is configured). Only one build runs at a time; others are rejected while one runs. Builds can be cancelled. Job history is in memory and lost on restart; workspaces and records stay in the cache directory.
- No login. Build-triggering requests are POST only, require a per-process CSRF token and a same-origin check, and are validated server-side. Every request on every listener must match an operator-controlled Host allowlist, including `0.0.0.0` behind loopback Docker/Kubernetes port-forwarding, so a rebound hostname cannot read CSRF tokens and forge same-origin mutations. Without `--allowed-host`, allow only `localhost`, `127.0.0.1`, and `[::1]` at any port. Explicit repeatable flags replace defaults; an entry without port allows any port, an entry with port requires that exact port. IPv6 literals are bracketed. Ingress operators list their external hostname and preserve Host; forwarded headers are never trusted. Host/CSRF/origin checks are not authentication. Access control remains the operator's network boundary (port-forward or an authenticating ingress). Read-only use needs no Cosign key.

**Container.** One image containing `lupetto`, `lupetto-explorer`, apko 1.4.5, Cosign v3.1.3, and CA certificates; non-root; cache directory on a mounted volume; Docker config and Cosign key mounted as files. No Docker daemon or socket. That apko builds work unprivileged inside the container must be verified, not assumed.

**Deferred.** Tekton task/PipelineRun execution, multi-architecture images, a database, multi-user authentication, unfixed-vulnerability scanning, and image deletion/retention.

## Production registry verification and signature status (user-approved 2026-10-02)

The user authorized closing the production-verification gate against a real registry, then adding signature status to the dashboard. This resolves the "signature/attestation verification status" and "SBOM download from registry attestations" items deferred by the [dashboard redesign](#dashboard-redesign-and-local-inventory-user-approved-2026-10-01). The CLI-only dashboard boundary, HTTP safety, and single-build rules still apply.

**Target and authorization.** Harbor v2.15.2 at `harbor.rbl.lol` (the user's home cluster), private project `lupetto`, repository prefix `lupetto/images`. Pushing, signing, and attesting there is authorized; other Harbor projects are not touched. Authentication uses project-scoped Harbor robot accounts: `robot$lupetto+push` (push/pull) stored by the user's `docker login` in Docker Desktop's `desktop` credential helper (macOS Keychain), which Lupetto reads through its existing Docker-config keychain, and a separate pull-only robot for the dashboard container, mounted as a Docker config file. No Lupetto authentication change.

**Network path (operator environment, not a Lupetto change).** Public DNS routes the name through Cloudflare; one edge address intermittently reset connections from the operator LAN (3/12 successes against 12/12 for the other edge and the LAN ingress). The operator host therefore maps `harbor.rbl.lol` to the LAN ingress in `/etc/hosts`, and the dashboard container gets the same `--add-host`. TLS is still verified normally against the publicly trusted certificate for the same name.

**Signing mode.** A new dedicated encrypted Cosign key pair outside the repository, used with upstream default services: no signing config, no HTTP allowance, so Cosign v3.1.3 obtains its trusted root and signing config through TUF and records entries in the **public Rekor** log. Entries are public and permanent (public key, digests, timestamps). The key password reaches Cosign only through the inherited `COSIGN_PASSWORD` environment. Production verification uses `cosign verify` / `verify-attestation` with the trusted public key and transparency-log verification (no `--insecure-ignore-tlog`).

**Trust for "Signed".** Exactly the public key of that pair, configured explicitly. Keyless identities, multiple keys, and fetching keys from the registry are out of scope.

**Dashboard deployment.** The LAN test deployment (`lupetto-lan-explorer` and `lupetto-lan-registry`, throwaway key) is replaced by one dashboard that reads Harbor. The user authorized stopping the test containers.

**Signature-status CLI fact.** `lupetto verify --json --cosign-public-key <file> <HOST/REPO@sha256:…>`, read-only, separate from `status`/`inspect` because it needs Cosign and trust configuration and costs network round trips to Rekor/TUF per image:

- The reference must be digest-addressed; tags, implicit Docker Hub names, and credentials are rejected exactly like `inspect`. The public key also comes from `LUPETTO_COSIGN_PUBLIC_KEY`, with the usual flag-over-environment precedence. Exactly Cosign v3.1.3 is required.
- Positive and `unsigned` verdicts are never inferred from Cosign error text. Lupetto first lists the image's Sigstore artifacts itself (OCI referrers, plus legacy `sha256-<digest>.sig`/`.att` tags) through its keychain, loopback-only HTTP guard, and sanitized errors. No signature artifact means `unsigned`. Otherwise `cosign verify --key` must succeed **and** the verified claim must name the same digest for `signed`; any other outcome with an artifact present is `invalid`. Registry/Cosign execution failures are `error`, never `unsigned`.
- The SPDX attestation is classified the same way (`attested` / `absent` / `invalid` / `error`), using `cosign verify-attestation --key --type spdxjson`. `attested` additionally requires the in-toto subject digest to equal the image digest and the predicate type to be SPDX. `--sbom-out <file>` writes the verified SPDX predicate (only from a verified attestation) as a new mode-0600 file; the document reports its SHA-256 and package count.
- Production behavior keeps Cosign defaults, including transparency-log verification. The local exception mirrors signing: `--cosign-allow-http` (literal loopback only) adds `--allow-http-registry --insecure-ignore-tlog`, and the document reports `transparencyLog: "verified"` or `"skipped-local"` so a local result is never presented as production evidence.
- Cosign stdout (verified payloads) is parsed with bounds; stderr is never printed, retained, or attached to errors, because it can echo registry or credential details. Its bounded prefix is only matched, on a non-zero exit, against fixed network/TLS, HTTP 5xx, registry-authorization, and TUF trust-root failure patterns, so that a registry, Rekor, or TUF outage is reported as `error` rather than `invalid` (decided during implementation). Errors are sanitized stage classifications. Invalid invocation exits 2 with no JSON; a completed check exits 0 even for `unsigned`/`invalid` (consumers read the states); global failures exit 1 with no JSON.
- The JSON document is `kind: "verify"`, `version: 1`: `reference`, `digest`, `checkedAt` (UTC RFC 3339), `trust` (`publicKeySHA256`: SHA-256 of the key's DER SubjectPublicKeyInfo), `transparencyLog` (`verified` / `skipped-local`), `signature` (`state`, optional sanitized `error`, `artifacts`: number of candidate signature artifacts found), and `attestation` (`state`, optional `error`, `artifacts`, optional `predicateType`, optional `sbom` with `sha256` of the exact predicate bytes, SPDX `packages` count, and `path` only when `--sbom-out` wrote it).
- Artifact classification (found during the [production run](verification.md#production-harbor-registry-and-public-rekor-verification-2026-10-02)): Cosign v3.1.3 stores signatures and attestations as DSSE Sigstore bundles in OCI referrers, annotated `dev.sigstore.bundle.predicateType` (`https://sigstore.dev/cosign/sign/v1` or the attestation predicate type), and `cosign verify --key` returns verified attestation claims too. A referrer is a signature candidate when that annotation is the sign type, an attestation candidate when it is the SPDX type, and both when the annotation is absent. Legacy `.sig` / `.att` tags are signature / attestation candidates. `signed` requires a verified claim naming the digest whose `critical.type` is `https://sigstore.dev/cosign/sign/v1` or the legacy simple-signing claim type `cosign container image signature` (non-bundle signing to a `.sig` tag; Cosign `verify` returns only signature claims in that format); an attestation-only image is `unsigned`. Accepting the legacy type (decided during implementation) avoids calling a correctly signed legacy image `invalid`; it was exercised with a real legacy signature on a loopback registry.

**Dashboard.** The dashboard gets trust only from `LUPETTO_COSIGN_PUBLIC_KEY` in its environment, passed to the CLI through the environment. Without it, every image shows **Not checked**. With it, the dashboard verifies the registry images it shows in the background, caches each result by key path and digest (discarding all results when the reported key fingerprint changes; positive results about 1 h, others including `invalid` about 5 min), and shows **Signed / Unsigned / Invalid / Not checked** (plus an error state) per image. Signed SBOMs are downloadable from the verified attestation. Signature status does not change track state or the build verdict.

## Proposed design choices

| ID | Proposal | Tradeoff |
| --- | --- | --- |
| P1 | Go for the CLI and Explorer, with independently runnable binaries. | Repository/module/product packaging remains open; SQLite driver selection affects CGO and cross-compilation. |
| P2 | Invoke pinned upstream tools instead of embedding their internals. | Smaller integration surface; tool compatibility and output handling need verification. |
| P3 | CLI-owned exact-build pipeline; Explorer invokes a documented CLI contract. | Avoids divergent semantics and imports of build internals; independent releases need explicit compatibility handling. |
| P4 | Package/version browsing first; Products and recipe history later. | Gets the core usable earlier without removing full-scope requirements. |
| P5 | Server-rendered Explorer with SQLite and bounded local jobs. | Fewer moving parts; not a multi-user remote build service. |
| P6 | Start with one explicit target architecture. | Reduces digest/SBOM association complexity; this does not establish a historical host restriction. |
| P7 | Major selection uses the highest matching APK version in a specified snapshot. | Predictable within that snapshot; exact family mapping and version rules still need definition. |

## Open decisions by dependency

### Scoped exact-build choices versus later contracts

The current Go/module, apko invocation, host-target mapping, repository trust, and minimal image choices are recorded above. The exact-build evidence format, retention, and SBOM composition behavior are resolved for the implemented local path. Runnable service recipes, a stable external machine-readable Explorer result contract, older supported Go/tool versions, and historical snapshot rebuild guarantees remain undecided; none are implied by the local `result.json`.

### Before catalog selectors

- SQLite driver and schema; snapshot identity and duplicate-import semantics.
- Catalog ingest/query command names and database selection flags.
- Catalog-specific package-family mappings and snapshot semantics beyond the implemented signed-index name/provider match and APK-compatible comparator.
- Missing historical APK behavior: explicit failure versus an explicitly designed archival input source; never silently substitute another version.

### Before publication/signing
