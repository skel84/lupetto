# Lupetto v0.3.1 release notes

v0.3.1 fixes a v0.3.0 regression: builds of some packages failed SPDX validation. The [changelog](../../CHANGELOG.md#v031-2026-10-23) lists both fixes.

## Fixes

### Builds of packages without SPDX origin entries

v0.3.0 rejected builds such as:

```text
lupetto build kubectl-1.33 1.33 --no-load
lupetto: build stage failed (workspace: …): validate SPDX against apko lock: SPDX missing installed APK entry kubectl-1.33@1.33.4-r3 (x86_64)
```

apko builds the image's SPDX document from the SBOM each installed package ships. Newer Wolfi package SBOMs describe the package with two purls, `distro=wolfi` and `origin=<origin package>`; older ones only with the first. Validation required an origin entry for every package as soon as one package had one. Since v0.3.0 the always-added `wolfi-baselayout` and `ca-certificates-bundle` have one, so any package with an older SBOM failed. A sample of 142 current Wolfi APKs found 8 such packages, among them `kubectl-1.33`, `helm` 4.0.1-r0, and `flux` 2.7.5-r1 ([evidence](../verification.md#optional-spdx-origin-entries-v031)).

Validation still requires exactly one `distro` entry for every APK in apko's lock, and rejects extra, duplicate, or changed entries of either kind. Only the requirement that every APK also have an `origin` entry is dropped.

### The cause of a failed publication build

A publication build that failed in a local stage printed only:

```text
lupetto: build stage failed (workspace: …): build failed
```

In a CI pipeline where the `--json` record was written to a discarded volume, the reason was lost. Stderr now carries the detailed cause of the build, SPDX validation, Docker load and tagging, and result-recording stages, as it always did without publication. `failure.json` and the `--json` record keep the sanitized message, and registry and Cosign errors stay sanitized.

## Upgrading from v0.3.0

No configuration or record changes. Tracks that failed to build with v0.3.0 build again. Images built by v0.3.0 are unaffected.
