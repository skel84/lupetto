# Lupetto v0.4.1 release notes

v0.4.1 fixes Explorer with a products file mounted from a Kubernetes ConfigMap, and makes a products file Explorer cannot read visible instead of silent. Images, build records, the status document, and the products-file format are unchanged from v0.4.0. The [changelog](../../CHANGELOG.md#v041-unreleased) lists every change.

## Fixed

### Products files mounted from a ConfigMap

A ConfigMap volume mounts each key as a symlink: `products.yaml -> ..data/products.yaml`, where `..data` points at a timestamped directory. `lupetto products list` in v0.4.0 refused that with "products file must be a regular file, not a directory or symlink". Explorer reads tracks through `products list`, so with a ConfigMap mounted read-only at `/etc/lupetto/products` it showed no tracks and scanned nothing.

`list` now follows symlinks and requires the target to be a regular file. `add` and `remove` still refuse a symlinked file: they replace the file by rename, which would replace the link rather than its target. A ConfigMap is read-only anyway: a tracking edit in Explorer fails with that message and the writable-directory hint, as with other read-only mounts.

If you worked around this by pointing `--products` at `/etc/lupetto/products/..data/products.yaml`, return to `/etc/lupetto/products/products.yaml` after upgrading. The `..data` path names kubelet internals and is not a stable interface.

### A products file Explorer cannot read

In v0.4.0 that failure looked like a different bug: the Vulnerabilities page said "No tracks", every track page answered 404 "track is not in the products file", the database stayed "Not downloaded yet", and nothing was logged. Now:

- The Vulnerabilities page shows the error in place of "No tracks".
- A track page answers **503** with the error, not 404.
- No scan runs until the file can be read again; earlier results are kept.
- Explorer logs the failure to stderr when it starts or changes, and logs once more when the file can be read again.
- `GET /metrics` exports `lupetto_products_load_success` (1 or 0) and `lupetto_products_load_timestamp_seconds`, without labels, also with `--scan-interval 0`. An alert on `lupetto_products_load_success == 0` catches this case.

## Upgrading from v0.4.0

Replace both the CLI and Explorer, or the combined container. Nothing else changes.
